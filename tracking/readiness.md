<details>
<summary>Proposal status</summary>

As of October 13, 2026, `main` has stayed at [`d1191c57`](https://github.com/eth-act/zkevm-standards/tree/d1191c57b5c19c13e4ad3520adf08fa75bb8db4d) since September 8, and every proposal open on September 21 remains open.

- **Failed termination function (`abort`) — 🟡:** Opened October 1, 2026, it requires the vendor static library to provide [`_Noreturn void abort(void)`](https://github.com/eth-act/zkevm-standards/blob/67937ac009c84f8b8300da109f97b864bbcb0d9f/standards/standard-termination-semantics/README.md#failed-termination-function), which ends execution as if `main` had returned a non-zero value. It has no reviews yet.
- **Host randomness — 🟡:** The proposal has been ready for review since October 5, 2026 but has no reviews yet. Its [September 28 revision](https://github.com/eth-act/zkevm-standards/commit/60f12bbe902190f22c6cfe4479c59b0b77a22afc) adds the `zkvm_random.h` header. [zkevm-test-monitor#49](https://github.com/eth-act/zkevm-test-monitor/pull/49) adds conformance tests, and draft [openvm#3165](https://github.com/openvm-org/openvm/pull/3165) implements the proposal.
- **Proving cost estimation — 🟡:** The proposal has one [approval](https://github.com/eth-act/zkevm-standards/pull/36#pullrequestreview-4885368715) and one [changes-requested review](https://github.com/eth-act/zkevm-standards/pull/36#pullrequestreview-4925406428), which objects to adding profiling scopes to the security-critical path. The [September 2 discussion](https://github.com/eth-act/zkevm-standards/pull/36#issuecomment-5510314744) leans toward an emulator-side standard. The text last changed on August 11.
- **Logging function — 🟡:** A June 11 [changes-requested review](https://github.com/eth-act/zkevm-standards/pull/27#pullrequestreview-4479048001) asks to keep the I/O standard minimal, and a [September 29 comment](https://github.com/eth-act/zkevm-standards/pull/27#issuecomment-5898965328) agrees. The text last changed on May 4.
- **Keccak-f[1600] permutation — 🟡:** A [September 24 comment](https://github.com/eth-act/zkevm-standards/pull/26#issuecomment-5811462923) asks for the function to return `void`. The text last changed on May 4.
- **U256 interface — 🟡:** The draft is [on hold](https://github.com/eth-act/zkevm-standards/pull/22#issuecomment-5818339574) until ZisK reports new measurements; in earlier tests, accelerating mul/div/rem cut median proving cost by about 0.03%.
- **Minimum memory resources — 🟡:** The draft uses placeholder sizes and is [on hold](https://github.com/eth-act/zkevm-standards/pull/20#issuecomment-5800108996) until Glamsterdam runs on mainnet or stateful EEST benchmarks exist; current benchmarks suggest about 512 MiB, assuming no bump allocator.

</details>

<details>
<summary>Ethrex</summary>

This review covers [`57101c1c` (`v29.0.1`)](https://github.com/lambdaclass/ethrex/tree/57101c1c2c199ebac8a827e6468341895972cb72) and its [release ELFs](https://github.com/lambdaclass/ethrex/releases/tag/v29.0.1), which carry a minisign signature for each ELF and verification key. The guest reaches each zkVM through [ere v0.18.1](https://github.com/eth-act/ere/tree/20e87aa7bcc09a8eac3bee2c941d8bfcf447e5ba) platform crates.

- **EEST tests passing across zkVMs — 🟡:** Ethrex v29.0.0 passes all 26,661 tests on SP1 v6.6.0 and 26,658 on both ZisK v1.2.0-alpha and OpenVM v2.1.0-preview. The three failures, `return50000`, `return50000_2`, and `static_return50000_2`, exhaust the heap under the bump allocators these zkVMs use by default ([issue #7177](https://github.com/lambdaclass/ethrex/issues/7177)); open [PR #7390](https://github.com/lambdaclass/ethrex/pull/7390) fixes them by reusing call buffers.
- **RISC-V target — 🟡:** The SP1 and OpenVM ELFs declare RV64IM (plus `zicclsm` on OpenVM). The ZisK ELF targets [`riscv64ima-zisk-zkvm-elf`](https://github.com/eth-act/ere/blob/20e87aa7bcc09a8eac3bee2c941d8bfcf447e5ba/crates/compiler/zisk/src/rust_rv64ima_customized.rs#L8-L9) and contains thousands of Zbb, Zbs, and Zbkb instructions such as `rori`, `andn`, and `rev8`, which the RV64IM target excludes. The ZisK ELFs in earlier Ethrex releases contain them too.
- **I/O interface — 🟡:** On ZisK, ere's [default `Platform` methods](https://github.com/eth-act/ere/blob/20e87aa7bcc09a8eac3bee2c941d8bfcf447e5ba/crates/platform/core/src/platform.rs#L14-L36) call the standard `read_input` and `write_output`. On SP1 and OpenVM, ere calls the SDK functions [`sp1_zkvm::io::read_vec`/`commit_slice`](https://github.com/eth-act/ere/blob/20e87aa7bcc09a8eac3bee2c941d8bfcf447e5ba/crates/platform/sp1/src/platform.rs#L10-L16) and [`openvm::io::read_vec`/`reveal_u64`](https://github.com/eth-act/ere/blob/20e87aa7bcc09a8eac3bee2c941d8bfcf447e5ba/crates/platform/openvm/src/platform.rs#L15-L30) instead.
- **Cryptographic accelerators C interface — 🟡:** On ZisK and SP1, the [crypto provider](https://github.com/lambdaclass/ethrex/blob/57101c1c2c199ebac8a827e6468341895972cb72/crates/guest-program/stateless-validator/src/crypto/zkvm_interface.rs) calls the standard `zkvm_*` functions; on ZisK, `mulmod256` also calls the ZisK-specific `mul_mod_bytes256_c`. On OpenVM, the guest [disables ere's standard implementation](https://github.com/lambdaclass/ethrex/blob/57101c1c2c199ebac8a827e6468341895972cb72/crates/guest-program/stateless-validator/bin/openvm/Cargo.toml#L17-L23) and calls OpenVM guest libraries directly, so the released OpenVM ELF has no `zkvm_*` symbols.
- **Standard entry point and vendor-library linking — 🔴:** The [release workflow](https://github.com/lambdaclass/ethrex/blob/57101c1c2c199ebac8a827e6468341895972cb72/.github/workflows/tag_release.yaml#L204-L221) builds every target with ere's `rust-customized` compiler, which uses each vendor's modified Rust toolchain and SDK crate rather than a generic compiler and the vendor static library. The ZisK and SP1 runtimes do call a C-ABI `main` from `_start`, and the ZisK build uses ZisK's linker script; OpenVM's [`__start`](https://github.com/openvm-org/openvm/blob/538c5488130da56c8442d33445efe3c1fe5ea8b8/crates/toolchain/openvm/src/lib.rs#L103-L115) ignores `main`'s return value.
- **Exit codes and language-level failure mapping — 🟡:** The guest reports invalid blocks in its output and returns 0 from `main` on every target. A Rust panic halts with code 1 on SP1 ([`sys_panic`](https://github.com/han0110/sp1/blob/b4f72fe1de5d6d26b3d3f531fcabd137b03e3338/crates/zkvm/entrypoint/src/syscalls/sys.rs#L56-L59)) and OpenVM ([`sys_panic`](https://github.com/openvm-org/openvm/blob/538c5488130da56c8442d33445efe3c1fe5ea8b8/crates/toolchain/openvm/src/pal_abi.rs#L47-L50)). In the released ZisK ELF, the panic path ends at an `unimp` instruction rather than the exit `ecall`, so a panic never reaches the standard non-zero exit.
- **Uses non-bump allocator — ❓:** ZisK uses the [ziskos bump allocator](https://github.com/0xPolygonHermez/zisk/blob/fbbc69bcd2ea9a78d1a438b4a897bc48ff0b00a3/ziskos/entrypoint/src/alloc/mod.rs#L6-L13) and OpenVM the [OpenVM bump allocator](https://github.com/openvm-org/openvm/blob/538c5488130da56c8442d33445efe3c1fe5ea8b8/crates/toolchain/platform/src/heap/mod.rs#L1-L5), because the guest enables neither embedded-allocator feature; SP1 uses sp1-zkvm's default [TLSF allocator](https://github.com/han0110/sp1/blob/b4f72fe1de5d6d26b3d3f531fcabd137b03e3338/crates/zkvm/entrypoint/src/allocators/embedded.rs#L1-L8). The handbook leaves this criterion undefined.

<summary>Zesu</summary>

This review covers zesu [`9e245b0c`](https://github.com/Consensys-Incorporated/zesu/tree/9e245b0c05a548a27de356dcd6629a847c96be2a) and zesu-zkvm [`73a8483a`](https://github.com/Consensys-Incorporated/zesu-zkvm/tree/73a8483a2720b4039181fc835d0ee49df84304f0), the commits behind the [`tests@v21.0.0` release](https://github.com/Consensys-Incorporated/zesu-zkvm/releases/tag/tests%40v21.0.0), which targets ZisK 1.2.0-alpha, OpenVM, and Linea.

- **EEST tests passing across zkVMs — 🟡:** Zesu `tests@v21.0.0` passes all 26,661 tests on ZisK v1.2.0-alpha. The dashboard has no OpenVM or SP1 results because [zkevm-benchmark-workload v0.18.1](https://github.com/eth-act/zkevm-benchmark-workload/blob/4a0ed18e73afb5c10f4f0f9dccb82d11652db274/README.md#L19-L20) runs Zesu only on ZisK.
- **Signed ELF and verification-key release assets — 🟡:** The release publishes minisign-signed ELFs for ZisK, OpenVM, and Linea but a signed verification key only for ZisK. The OpenVM and Linea file names use the placeholder version `ALPHA`. The [release workflow](https://github.com/Consensys-Incorporated/zesu-zkvm/blob/73a8483a2720b4039181fc835d0ee49df84304f0/.github/workflows/release.yml#L21-L33) says ere rejects the 64-bit OpenVM ELF and lacks Linea support; open [PR #40](https://github.com/Consensys-Incorporated/zesu-zkvm/pull/40) states that ere v0.17.0 accepts the OpenVM ELF but adds no key-generation step.
- **RISC-V target — 🟡:** The OpenVM and Linea ELFs declare `rv64im_zicclsm`, but the ZisK ELF links an object [built with Zbb and Zbs](https://github.com/Consensys-Incorporated/zesu/blob/9e245b0c05a548a27de356dcd6629a847c96be2a/build.zig#L757-L767). The [ZisK host build](https://github.com/Consensys-Incorporated/zesu-zkvm/blob/73a8483a2720b4039181fc835d0ee49df84304f0/zisk/build.zig#L5-L12) also removes `c` but keeps `zca`, so `zkvm_abort` and `zkvm_log` contain 18 compressed instructions.
- **Accelerated memory operations — 🟡:** On ZisK, `memcpy`, `memmove`, and `memcmp` resolve to ZisK's DMA routines because the build [merges the vendor library with `--whole-archive`](https://github.com/Consensys-Incorporated/zesu-zkvm/blob/73a8483a2720b4039181fc835d0ee49df84304f0/zisk/build.zig#L38-L51). The ZisK object, however, also [inlines ZisK DMA instructions](https://github.com/Consensys-Incorporated/zesu/blob/9e245b0c05a548a27de356dcd6629a847c96be2a/src/evm/primitives/dma.zig#L1-L40) for the 32-byte copies in [`DUP` and `SWAP`](https://github.com/Consensys-Incorporated/zesu/blob/9e245b0c05a548a27de356dcd6629a847c96be2a/src/evm/interpreter/stack.zig#L192-L214), which bypass the standard symbols.
- **Standard entry point and vendor-library linking — 🟡:** On ZisK, the guest links ZisK's static library, whose `_start` calls Zesu's `int main(void)`, but uses its own [linker script](https://github.com/Consensys-Incorporated/zesu-zkvm/blob/73a8483a2720b4039181fc835d0ee49df84304f0/zisk/zisk.ld#L119-L154) with heap symbols `ZKVM_HEAP_POS` and `ZKVM_HEAP_TOP` instead of `_heap_start` and `_heap_end`. OpenVM and Linea have no vendor library, so zesu-zkvm supplies its own [`_start`](https://github.com/Consensys-Incorporated/zesu-zkvm/blob/73a8483a2720b4039181fc835d0ee49df84304f0/openvm/src/startup.S#L12-L25), linker scripts, I/O, and accelerators for them.
- **Exit codes and language-level failure mapping — 🟡:** [`main` returns 1 on an error, and panics call `zkvm_abort`](https://github.com/Consensys-Incorporated/zesu/blob/9e245b0c05a548a27de356dcd6629a847c96be2a/src/zkvm/root.zig#L39-L53), which each target implements as an exit with code 1. But the [release objects use `ReleaseFast`](https://github.com/Consensys-Incorporated/zesu/blob/9e245b0c05a548a27de356dcd6629a847c96be2a/.github/workflows/release-object.yml#L37-L41), which disables Zig's runtime safety checks, so out-of-bounds accesses, integer overflow, and `unreachable` become undefined behavior instead of panics.
- **Uses non-bump allocator — ❓:** The guest uses a [segregated free-list allocator](https://github.com/Consensys-Incorporated/zesu/blob/9e245b0c05a548a27de356dcd6629a847c96be2a/src/zkvm/alt_fl_alloc.zig#L97-L153) that reuses freed blocks in power-of-two classes from 8 B to 16 MiB and never reclaims larger requests. The handbook leaves this criterion undefined.

</details>

<summary>Nethermind</summary>

This review covers [`5c2a2768`](https://github.com/NethermindEth/nethermind/tree/5c2a2768fdac1930af35aadf609b61bc6f4af8ee), the commit behind the [`zkvm-guests-2.1.0-unstable-5c2a2768` release](https://github.com/NethermindEth/nethermind/releases/tag/zkvm-guests-2.1.0-unstable-5c2a2768), which targets ZisK 1.3.0-alpha, SP1 v6.5.0, and OpenVM. [bflat-riscv64](https://github.com/NethermindEth/bflat-riscv64/tree/e48bd7b555baa1a592e9825240ca16ce4b012247) compiles the C# code ahead of time with .NET NativeAOT for `rv64im`, then links musl, bflat's runtime modules and per-zkVM entry points, and a runtime package for each zkVM.

- **EEST tests passing across zkVMs — 🔴:** The dashboard has Nethermind EL witness results but no Nethermind guest results. [zkevm-benchmark-workload v0.18.1](https://github.com/eth-act/zkevm-benchmark-workload/blob/4a0ed18e73afb5c10f4f0f9dccb82d11652db274/crates/benchmark-runner/src/stateless_validator.rs#L19-L28) supports only the Reth, Ethrex, Zesu, and Nimbus guests, and no PR in ere-guests or the workload adds Nethermind.
- **MIT + Apache 2.0 dual licensing — 🔴:** The [guest source](https://github.com/NethermindEth/nethermind/blob/5c2a2768fdac1930af35aadf609b61bc6f4af8ee/src/Nethermind/Nethermind.Stateless.Guest/Program.cs#L1-L2) is LGPL-3.0-only. The ELFs also link runtime modules from bflat-riscv64, whose [repository license](https://github.com/NethermindEth/bflat-riscv64/blob/e48bd7b555baa1a592e9825240ca16ce4b012247/LICENSE) is AGPL-3.0.
- **Signed ELF and verification-key release assets — 🟡:** The release publishes GPG-signed archives with ZisK, SP1, and OpenVM ELFs, but the [release workflow](https://github.com/NethermindEth/nethermind/blob/5c2a2768fdac1930af35aadf609b61bc6f4af8ee/.github/workflows/release-zkvm-guests.yml#L50-L92) generates no verification keys, and asset names do not follow the handbook's `stateless-validator-<guestName>-<zkVMName>-<zkVMVersion>` pattern.
- **Cryptographic accelerators C interface — 🟡:** Precompiles call the standard functions through [Nethermind.Zkvm.Abstractions](https://github.com/NethermindEth/zkvm-abstractions/blob/c62c606e77c465aa9c552b7652727c3f94e08681/src/Accelerators.bindings.cs), but [Keccak hashing](https://github.com/NethermindEth/nethermind/blob/5c2a2768fdac1930af35aadf609b61bc6f4af8ee/src/Nethermind/Nethermind.Core/Crypto/KeccakHash.zkevm.cs#L14) calls the ZisK-named permutation [`syscall_keccak_f`](https://github.com/NethermindEth/zkvm-abstractions/blob/c62c606e77c465aa9c552b7652727c3f94e08681/src/Accelerators.cs#L242-L254) instead of `zkvm_keccak256`, and bflat [forwards that name](https://github.com/NethermindEth/bflat-riscv64/blob/e48bd7b555baa1a592e9825240ca16ce4b012247/src/bflat/modules/zkvm_sp1/module.S#L43-L62) to SP1's and OpenVM's own permutation functions.
- **Accelerated memory operations — 🟡:** On ZisK, bflat [wraps the four memory functions](https://github.com/NethermindEth/bflat-libziskos/blob/ab540fe3f7bec427c63b2499c7adb2a49d9e1719/bflat-manifest.json#L10) to ZisK's DMA routines, and its JIT [inlines ZisK's DMA compare instruction](https://github.com/NethermindEth/bflat-riscv64/blob/e48bd7b555baa1a592e9825240ca16ce4b012247/src/bflat/BuildCommand.cs#L1422-L1434). On SP1, bflat-sp1 [makes SP1's `memcpy` local](https://github.com/NethermindEth/bflat-sp1/blob/db8fd41ca4e42e90e86c76b000157cf3eac26637/README.md#why-some-symbols-are-localized), so musl's version replaces the vendor implementation.
- **Standard entry point and vendor-library linking — 🔴:** For each zkVM, bflat supplies its own [`_start`](https://github.com/NethermindEth/bflat-riscv64/blob/e48bd7b555baa1a592e9825240ca16ce4b012247/src/bflat/modules/zkvm_zisk/module.S#L21-L46) and [linker script](https://github.com/NethermindEth/bflat-riscv64/blob/e48bd7b555baa1a592e9825240ca16ce4b012247/src/bflat/modules/zkvm_zisk/script.ld#L164-L178) with non-standard heap symbols, and bflat [rebuilds the ZisK library without ZisK's `_start`](https://github.com/NethermindEth/bflat-libziskos/blob/ab540fe3f7bec427c63b2499c7adb2a49d9e1719/build/entrypoint.patch#L23-L31). On ZisK, this layout puts `.data` and `.bss` in ZisK's [reserved stack region](https://github.com/0xPolygonHermez/zisk/blob/02d2ae7b711454ce4574d852f8bfbddbfcbb1d67/ziskbuild/zisk_linker_script.ld#L40-L53) and the guest's stack across ZisK's register and output regions.
- **ELF artifact compliance — 🟡:** The [linker scripts mark `.bss` as `NOLOAD` outside every `PT_LOAD` segment](https://github.com/NethermindEth/bflat-riscv64/blob/e48bd7b555baa1a592e9825240ca16ce4b012247/src/bflat/modules/zkvm_sp1/script.ld#L182-L194). In each released ELF, about 2.2 MiB of zero-initialized data therefore relies on zkVM memory starting at zero, instead of a `p_memsz > p_filesz` tail as the standard requires.
- **Exit codes and language-level failure mapping — 🔴:** The [shared entry point](https://github.com/NethermindEth/nethermind/blob/5c2a2768fdac1930af35aadf609b61bc6f4af8ee/src/Nethermind/Nethermind.Stateless.Guest/Program.cs#L24-L73) returns 0, and its `ZkvmThrow` handler turns any unhandled exception into a failed-validation output with exit code 0. Non-zero exits occur only before any failure output exists, on a second exception, or on a [runtime fail-fast](https://github.com/NethermindEth/bflat-riscv64/blob/e48bd7b555baa1a592e9825240ca16ce4b012247/src/bflat/modules/rhp/module.c#L238-L275) or abort.
- **Uses non-bump allocator — ❓:** The guest uses a bump allocator: bflat's [`free` is a no-op](https://github.com/NethermindEth/bflat-riscv64/blob/e48bd7b555baa1a592e9825240ca16ce4b012247/src/bflat/modules/pal/module.c#L261-L268), and its [GC never collects](https://github.com/NethermindEth/bflat-riscv64/blob/e48bd7b555baa1a592e9825240ca16ce4b012247/docs/modules.md#L568-L582). The handbook leaves this criterion undefined.

<summary>evm-asm</summary>

This review covers [`7e65e4d0`](https://github.com/Verified-zkEVM/evm-asm/tree/7e65e4d024718f704226cd795f3d03d4e9aafe13), the head of `main` since September 4. evm-asm generates RV64 assembly from Lean and targets only ZisK: CI links a `stateless_guest.elf` that reads the SSZ stateless input, and the project runs it on `ziskemu`. Lean proofs cover the RV64 core and per-opcode handlers, but the [stateless-guest routines remain unproved](https://github.com/Verified-zkEVM/evm-asm/blob/7e65e4d024718f704226cd795f3d03d4e9aafe13/README.md?plain=1#L304-L416), and the [README](https://github.com/Verified-zkEVM/evm-asm/blob/7e65e4d024718f704226cd795f3d03d4e9aafe13/README.md?plain=1#L3-L5) says the team is reconsidering the project's direction.

- **EEST tests passing across zkVMs — 🔴:** The dashboard has no evm-asm guest results. [zkevm-benchmark-workload v0.18.1](https://github.com/eth-act/zkevm-benchmark-workload/blob/4a0ed18e73afb5c10f4f0f9dccb82d11652db274/crates/benchmark-runner/src/stateless_validator.rs#L19-L28) supports only the Reth, Ethrex, Zesu, and Nimbus guests, and no PR in ere-guests or the workload adds evm-asm.
- **MIT + Apache 2.0 dual licensing — 🔴:** The [repository license](https://github.com/Verified-zkEVM/evm-asm/blob/7e65e4d024718f704226cd795f3d03d4e9aafe13/LICENSE) is MIT-only, and no issue or PR proposes adding Apache 2.0.
- **Signed ELF and verification-key release assets — 🔴:** The repository has no GitHub releases, only date tags such as `r20260819`. The ELF ships only inside a Docker image that [`docker.yml`](https://github.com/Verified-zkEVM/evm-asm/blob/7e65e4d024718f704226cd795f3d03d4e9aafe13/.github/workflows/docker.yml) pushes to GHCR without a signature or verification key, and GHCR refuses anonymous pulls of that image.
- **RISC-V target — 🟡:** The generator [disables compressed instructions](https://github.com/Verified-zkEVM/evm-asm/blob/7e65e4d024718f704226cd795f3d03d4e9aafe13/EvmAsm/Codegen/Layout.lean#L130-L136) and emits RV64IM code, but it [assembles with `-march=rv64imac`](https://github.com/Verified-zkEVM/evm-asm/blob/7e65e4d024718f704226cd795f3d03d4e9aafe13/EvmAsm/Codegen/Driver.lean#L84-L85) and places [ZisK `csrrs` accelerator instructions](https://github.com/Verified-zkEVM/evm-asm/blob/7e65e4d024718f704226cd795f3d03d4e9aafe13/EvmAsm/Codegen/Emit.lean#L158-L162) in guest code.
- **I/O interface — 🔴:** The guest never calls `read_input` or `write_output`: it [reads ZisK's memory-mapped input at `0x40000000`](https://github.com/Verified-zkEVM/evm-asm/blob/7e65e4d024718f704226cd795f3d03d4e9aafe13/EvmAsm/Codegen/Programs/StatelessGuestData.lean#L566) and [writes its result to ZisK's output region](https://github.com/Verified-zkEVM/evm-asm/blob/7e65e4d024718f704226cd795f3d03d4e9aafe13/EvmAsm/Codegen/Programs/Registry.lean#L972).
- **Cryptographic accelerators C interface — 🔴:** The guest invokes ZisK precompiles directly with `csrrs` instructions. Its `zkvm_sha256` and `zkvm_keccak256` are [guest-defined assembly routines](https://github.com/Verified-zkEVM/evm-asm/blob/7e65e4d024718f704226cd795f3d03d4e9aafe13/EvmAsm/Codegen/Programs/HashBridgeProg.lean#L38-L84) over ZisK's CSRs, not the vendor library's C functions.
- **Accelerated memory operations — 🔴:** The guest links neither a C library nor a vendor archive and copies memory with its own [`sg_memcpy`](https://github.com/Verified-zkEVM/evm-asm/blob/7e65e4d024718f704226cd795f3d03d4e9aafe13/EvmAsm/Codegen/Programs/Registry.lean#L1006) and per-type loops, so a vendor implementation cannot take effect.
- **Standard entry point and vendor-library linking — 🔴:** The guest defines [its own `_start`](https://github.com/Verified-zkEVM/evm-asm/blob/7e65e4d024718f704226cd795f3d03d4e9aafe13/EvmAsm/Codegen/Layout.lean#L130-L136) and has no `main`, and the [link step](https://github.com/Verified-zkEVM/evm-asm/blob/7e65e4d024718f704226cd795f3d03d4e9aafe13/EvmAsm/Codegen/Driver.lean#L68-L100) passes only the guest object with `-nostdlib` and hardcoded ZisK addresses, without a vendor library or linker script.
- **ELF artifact compliance — ❓:** No published ELF exists to inspect. The [link step](https://github.com/Verified-zkEVM/evm-asm/blob/7e65e4d024718f704226cd795f3d03d4e9aafe13/EvmAsm/Codegen/Driver.lean#L84-L100) relies on GNU ld's default script with section-address overrides and no `PHDRS`.
- **Exit codes and language-level failure mapping — 🔴:** Every halt site in the generator, including the [default halt stub](https://github.com/Verified-zkEVM/evm-asm/blob/7e65e4d024718f704226cd795f3d03d4e9aafe13/EvmAsm/Codegen/Layout.lean#L120-L128), issues ZisK's exit `ecall` with `a0 = 0`, so the guest has no path that reports abnormal termination.
- **Uses non-bump allocator — ❓:** The guest has no heap allocator; it uses [fixed-capacity arenas](https://github.com/Verified-zkEVM/evm-asm/blob/7e65e4d024718f704226cd795f3d03d4e9aafe13/EvmAsm/Codegen/ArenaCapacities.lean) at fixed addresses. The handbook leaves this criterion undefined.

The glue, however, truncates the status to 8 bits, so an exit status of 256 would halt as success.

The handbook leaves this criterion undefined.

<summary>ZisK</summary>

This review covers [`1e22630b` (`v1.3.2-alpha`)](https://github.com/0xPolygonHermez/zisk/tree/1e22630bb7e143c30705a1603ed87cfd3da8c6ec), the latest release and the head of `main`. Since `v1.3.0-alpha` (`02d2ae7b`), the version the test monitor ran, ZisK has fixed circuit soundness bugs but left `ziskos`, `ziskbuild`, the transpilers, and the emulator unchanged, so the monitor results still apply to the code that implements the standards.

The RISC-V status reflects the latest [standard ISA run](https://eth-act.github.io/zkevm-test-monitor/zkvm.html?name=zisk&suite=act4-standard&run=latest), of September 28, 2026, in which all 72 tests pass execution, proving, and verification, both directly and through ere. The [eth-act standards run](https://eth-act.github.io/zkevm-test-monitor/zkvm.html?name=zisk&suite=eth-act-standards&run=latest) of October 1, 2026 passes 43 of 49 tests. `accel-blake2f` fails because [`zkvm_blake2f`](https://github.com/0xPolygonHermez/zisk/blob/1e22630bb7e143c30705a1603ed87cfd3da8c6ec/ziskos/entrypoint/src/zisklib/lib/zkvm_accelerators.rs#L411-L475) returns success for a final flag of 2, which the test rejects by the EIP-152 rule; the C interface header lists only 0 and 1 and leaves other values undefined. `accel-bls12-g2-msm` and `mem-memcmp` execute correctly but fail to prove; the monitor [attributes this](https://github.com/eth-act/zkevm-test-monitor/commit/3f85446749b8580cd0836ddbe58622fa9514f22f) to a fixed-size GPU buffer in ZisK's prover.

- **Host randomness — 🔴:** The library exports no `zkvm_random_u64`, and [`sys_rand`](https://github.com/0xPolygonHermez/zisk/blob/1e22630bb7e143c30705a1603ed87cfd3da8c6ec/ziskos/entrypoint/src/lib.rs#L583-L594) seeds a guest-side generator with a constant, so every execution draws the same values. On `v1.3.0-alpha`, all six of the monitor's unmerged [randomness tests](https://github.com/eth-act/zkevm-test-monitor/pull/49) fail, and draft [PR #1384](https://github.com/0xPolygonHermez/zisk/pull/1384) adds a host-drawn seed per execution.
- **Documented cluster-mode support tested on the EF cluster — 🟡:** [ZisK](https://github.com/0xPolygonHermez/zisk/blob/1e22630bb7e143c30705a1603ed87cfd3da8c6ec/book/getting_started/distributed_execution.md) and [Provoor](https://github.com/han0110/provoor/blob/7fc2b947123104b0d91dc4fa37b3f91e2a4995bb/docs/zkvm/zisk.md) document cluster deployment, and a [Provoor run](https://github.com/han0110/provoor-runs/blob/1de75b70e6cce3e387574bcb973c0e9d7434d31f/results/runs/1791346793_919f3334_ethrex-zisk/config.json) on October 7 proved and verified 1,000 Sepolia blocks with `v1.3.1-alpha` on four hosts with four RTX 5090s each, as the reference cluster specifies. The published results do not identify the cluster as the EF's.
- **I/O interface — 🟡:** [`write_output`](https://github.com/0xPolygonHermez/zisk/blob/1e22630bb7e143c30705a1603ed87cfd3da8c6ec/ziskos/entrypoint/src/zisklib/lib/zkvm_io.rs#L90-L123) packs bytes into public-output words through [`set_output`, which asserts fewer than 64 words](https://github.com/0xPolygonHermez/zisk/blob/1e22630bb7e143c30705a1603ed87cfd3da8c6ec/ziskos/entrypoint/src/lib.rs#L329-L349), so output stops at 256 bytes. In the standards run, the three tests that write more than 256 bytes terminate abnormally, and the other 12 I/O tests pass through verification. The standard specifies concatenated output without that cap and requires every `write_output` call to succeed.
- **Static library and linker script — 🟡:** The [linker script](https://github.com/0xPolygonHermez/zisk/blob/1e22630bb7e143c30705a1603ed87cfd3da8c6ec/ziskbuild/zisk_linker_script.ld#L140-L142) defines `_heap_bottom` / `_heap_top` instead of the required `_heap_start` / `_heap_end`; the unreleased `pre-develop-1.4.0-alpha` branch [adds them](https://github.com/0xPolygonHermez/zisk/blob/a7fdf2687b40907dfaccba7dd87298a0b0ad4bcd/ziskbuild/zisk_linker_script.ld#L149-L162). With GNU ld, a guest without initialized data gets an empty segment at address 0 that `ziskemu` rejects, so the monitor [patches the script](https://github.com/eth-act/zkevm-test-monitor/issues/58). The I/O cap and termination gaps also apply.
- **ELF loading and validation — 🟡:** The [loader](https://github.com/0xPolygonHermez/zisk/blob/1e22630bb7e143c30705a1603ed87cfd3da8c6ec/transpilers/common/src/elf_extraction.rs#L116-L123) accepts both `PF_X` and `PF_X | PF_R` executable segments, warning on the second, whereas the standard requires a zkVM to accept exactly one combination.
- **Execution termination semantics — 🟡:** The [exit handler](https://github.com/0xPolygonHermez/zisk/blob/1e22630bb7e143c30705a1603ed87cfd3da8c6ec/transpilers/riscv/src/riscv2zisk_context.rs#L3155-L3168) checks only `a7 == 93` and ends successfully whatever `a0` holds, and the monitor's unmerged [termination tests](https://github.com/eth-act/zkevm-test-monitor/blob/b41462a50e3e69b24faf933f2f30759141ac6ccf/results/history/zisk-eth-act-standards.json#L106-L107) show guests whose `main` returns 1 or 7 finishing normally. The transpiler also turns [`ebreak`](https://github.com/0xPolygonHermez/zisk/blob/1e22630bb7e143c30705a1603ed87cfd3da8c6ec/transpilers/riscv/src/riscv2zisk_context.rs#L243) into a no-op and [continues past `unimp`](https://github.com/0xPolygonHermez/zisk/blob/1e22630bb7e143c30705a1603ed87cfd3da8c6ec/transpilers/riscv/src/riscv2zisk_context.rs#L1608-L1622), the traps behind C `abort()`, Rust aborts, and the [static library's panic handler](https://github.com/0xPolygonHermez/zisk/blob/1e22630bb7e143c30705a1603ed87cfd3da8c6ec/ziskos-staticlib/src/lib.rs#L20-L26). [PR #1375](https://github.com/0xPolygonHermez/zisk/pull/1375), merged into `pre-develop-1.4.0-alpha` on October 13, 2026, halts on all three, but it is unreleased, and no run has proved it end to end.

The other reviewed rows remain unknown:

- **Final proof size ≤300 KiB — ❓:** ere verifies ZisK's [uncompressed `VadcopFinal` proof](https://github.com/eth-act/ere/blob/c0c411ae9215e0f72a00d52e32e267b30ef48606/crates/verifier/zisk/src/proof.rs#L21-L29), and its [`v1.3.1-alpha` test proof](https://github.com/eth-act/ere/blob/c0c411ae9215e0f72a00d52e32e267b30ef48606/crates/verifier/zisk/tests/fixtures/proof.bin) is 831,511 bytes (812 KiB). ZisK [documents recursive proof compression](https://github.com/0xPolygonHermez/zisk/blob/02d2ae7b711454ce4574d852f8bfbddbfcbb1d67/book/getting_started/quickstart.md#compressed-proof-optional). [PR #1381](https://github.com/0xPolygonHermez/zisk/pull/1381), merged into `pre-develop-1.4.0-alpha` on October 13, 2026, adds a compressed proof for the blake3 hash family that ere uses, but no measured size exists for the L1 configuration.
- **Memory safety guard regions — ❓:** The [linker places the stack at the start of RAM](https://github.com/0xPolygonHermez/zisk/blob/1e22630bb7e143c30705a1603ed87cfd3da8c6ec/ziskbuild/zisk_linker_script.ld#L97-L106), leaving the region below it unmapped, and the emulator faults on the monitor's NULL-pointer tests. Those tests ran execution only, so no test has checked fault behavior in either region through proof verification.
- **Instruction address misaligned exception semantics — ❓:** [JALR clears only bit 0](https://github.com/0xPolygonHermez/zisk/blob/1e22630bb7e143c30705a1603ed87cfd3da8c6ec/transpilers/riscv/src/riscv2zisk_context.rs#L1468-L1541), and the transpiler decodes compressed instructions, so under ZisK's own ISA every jump target is 2-byte aligned. Whether that satisfies the standard for an RV64IM guest, where a target at 2 mod 4 must terminate, is unsettled; the monitor's exception tests (open [PR #33](https://github.com/eth-act/zkevm-test-monitor/pull/33)) run only on a fork.

<summary>OpenVM</summary>

This review covers [`538c5488` (`v2.1.0-preview`)](https://github.com/openvm-org/openvm/tree/538c5488130da56c8442d33445efe3c1fe5ea8b8), still the only RV64 release. The RV64 development branch [`develop-v2.x.0` at `2eb14071`](https://github.com/openvm-org/openvm/tree/2eb140715d77db5f92c9f72a5fb5c0262393feda) leaves every gap below unchanged; `main` and the `v2.1.0-rc` tags are the RV32 line. The [ISA monitor](https://github.com/eth-act/zkevm-test-monitor/blob/0d09b4363a5a4392aba2a7d28102700314f75fd5/config.json#L20-L33) now builds [`han0110/openvm` at `a391b22e`](https://github.com/han0110/openvm/commit/a391b22ebb5305fa52d3394abfd0810df4baff90), the source ere proves with: `v2.1.0-preview` plus one commit that changes only dependency sources. The [latest standard ISA run](https://eth-act.github.io/zkevm-test-monitor/zkvm.html?name=openvm&suite=act4-standard&run=latest), through ere on September 29, 2026, executes, proves, and verifies all 72 tests with ACT4 4.1.0. The ISA tests miss one documented RV64I deviation: JALR, loads, and stores reject a base register whose upper 32 bits are nonzero ([monitor issue #53](https://github.com/eth-act/zkevm-test-monitor/issues/53)); open [PR #3163](https://github.com/openvm-org/openvm/pull/3163) fixes it on `develop-v2.x.0` and changes the verification key.

OpenVM ships no C library for guests, so the [October 1 eth-act standards run](https://eth-act.github.io/zkevm-test-monitor/zkvm.html?name=openvm&suite=eth-act-standards&run=latest) tests [ere's C layer over OpenVM's guest libraries](https://github.com/eth-act/zkevm-test-monitor/blob/0d09b4363a5a4392aba2a7d28102700314f75fd5/tests/eth-act-standards/README.md#L153-L165); the notes below separate ere's failures from OpenVM's.

- **Host randomness — 🟡:** [`sys_rand` and `hint_random`](https://github.com/openvm-org/openvm/blob/538c5488130da56c8442d33445efe3c1fe5ea8b8/crates/toolchain/openvm/src/pal_abi.rs#L29-L41) take random bytes from the host, but the host [seeds its RNG with zero](https://github.com/openvm-org/openvm/blob/538c5488130da56c8442d33445efe3c1fe5ea8b8/crates/vm/src/arch/state.rs#L34) for every execution, and the guest crate exports no `zkvm_random_u64`. On the monitor's unmerged [randomness tests](https://github.com/eth-act/zkevm-test-monitor/pull/49), a wrapper over `hint_random` fails `rand-independence` because two executions return the same values. Draft [PR #3165](https://github.com/openvm-org/openvm/pull/3165) adds a per-run seed and the export.
- **Documented cluster-mode support tested on the EF cluster — 🟡:** [Provoor documents OpenVM 2.1.0-preview cluster deployment](https://github.com/han0110/provoor/blob/7fc2b947123104b0d91dc4fa37b3f91e2a4995bb/docs/zkvm/openvm.md) through a patched fork of [Axiom Edge](https://github.com/axiom-crypto/axiom-edge/tree/2061a3a494afdc13706d86201776032769b1b4a7), and a [Provoor run](https://github.com/han0110/provoor-runs/blob/1de75b70e6cce3e387574bcb973c0e9d7434d31f/results/runs/1791357703_bf95521c_ethrex-openvm/config.json) on October 7 proved 1,000 Sepolia blocks on four hosts with four RTX 5090s each, as the reference cluster specifies. The published results do not identify the cluster as the EF's.
- **I/O interface — 🔴:** OpenVM provides only [Rust I/O](https://github.com/openvm-org/openvm/blob/538c5488130da56c8442d33445efe3c1fe5ea8b8/crates/toolchain/openvm/src/io/mod.rs) and no `read_input` or `write_output`. Through ere's layer, 12 of 15 I/O tests pass; the three tests that write more than 256 bytes hit [ere's output cap](https://github.com/eth-act/ere/blob/e49696e5e1bfedbfd6a8f4009140b72005ce72e3/crates/platform/openvm/src/platform.rs#L19-L24), not an OpenVM limit.
- **Cryptographic accelerators C interface — 🟡:** The OpenVM team's [`openvm-accelerators` crate](https://github.com/axiom-crypto/openvm-eth/blob/ed7f32a4021fcd22d0855077c36584d63c57fe43/crates/accelerators/src/lib.rs#L21-L44) exports all 19 `zkvm_*` functions on the `develop-v2.1.0` branch of `axiom-crypto/openvm-eth` ([PR #694](https://github.com/axiom-crypto/openvm-eth/pull/694), merged August 12, 2026, replacing the closed openvm PRs #3075–#3080). No OpenVM release or static library ships it, and no monitor run covers it. The monitor instead tests ere's separate implementation, which passes 18 of 19 functions; the `blake2f` failure is ere's.
- **Accelerated memory operations — 🟡:** [`openvm-mem`](https://github.com/openvm-org/openvm/blob/538c5488130da56c8442d33445efe3c1fe5ea8b8/crates/toolchain/mem/src/lib.rs#L112-L114) defines `memcpy`, `memmove`, `memset`, and `memcmp`, and the monitor's eight semantic tests of these routines pass. The `openvm` crate, however, [relies on link order](https://github.com/openvm-org/openvm/blob/538c5488130da56c8442d33445efe3c1fe5ea8b8/crates/toolchain/openvm/src/lib.rs#L35-L38) to override `compiler_builtins`, which the standard does not accept, and all four `mem-link-*` tests fail because the strong symbols sit outside the object that holds `_start`.
- **Static library and linker script — 🔴:** OpenVM provides neither. Guests link with the linker's default script and [`-Ttext=0x00200800`](https://github.com/openvm-org/openvm/blob/538c5488130da56c8442d33445efe3c1fe5ea8b8/crates/toolchain/build/src/lib.rs#L335), so the ELF has no `_heap_start`/`_heap_end` symbols and no code/read-only-data segment split. [`_start`](https://github.com/openvm-org/openvm/blob/538c5488130da56c8442d33445efe3c1fe5ea8b8/crates/toolchain/openvm/src/lib.rs#L101-L115) also drops `main`'s return value.
- **Memory layout restrictions — 🔴:** The standard requires each vendor to publish a linker script that describes its memory regions. OpenVM fixes its layout in [platform constants](https://github.com/openvm-org/openvm/blob/538c5488130da56c8442d33445efe3c1fe5ea8b8/crates/toolchain/platform/src/memory.rs#L1-L10) and build flags and publishes no linker script.
- **Memory safety guard regions — 🔴:** In the standards run, `accel-null-keccak256-output` passes a NULL output pointer to [ere's `zkvm_keccak256`](https://github.com/eth-act/ere/blob/e49696e5e1bfedbfd6a8f4009140b72005ce72e3/crates/platform/openvm/src/zkvm_accelerator.rs#L88-L95), which stores 32 bytes at address 0, and OpenVM finishes the execution normally. The executor's [address check](https://github.com/openvm-org/openvm/blob/538c5488130da56c8442d33445efe3c1fe5ea8b8/extensions/riscv/circuit/src/adapters/mod.rs#L287-L302) has only an upper bound, and the stack [starts at `0x200400`](https://github.com/openvm-org/openvm/blob/538c5488130da56c8442d33445efe3c1fe5ea8b8/crates/toolchain/platform/src/memory.rs#L6-L7) and grows down to address 0 with no guard region.
- **ELF loading and validation — 🟡:** The [loader](https://github.com/openvm-org/openvm/blob/538c5488130da56c8442d33445efe3c1fe5ea8b8/crates/toolchain/transpiler/src/elf.rs) validates ELF64/RISC-V executable headers and loads `PT_LOAD` segments, but [classifies permissions by `PF_X` alone](https://github.com/openvm-org/openvm/blob/538c5488130da56c8442d33445efe3c1fe5ea8b8/crates/toolchain/transpiler/src/elf.rs#L197). It accepts writable executable segments, overlapping segments, and both `PF_X` and `PF_X | PF_R`, and it never checks that `e_entry` lies in an executable segment.
- **Execution termination semantics — 🟡:** The [runtime](https://github.com/openvm-org/openvm/blob/538c5488130da56c8442d33445efe3c1fe5ea8b8/crates/toolchain/openvm/src/lib.rs#L101-L115) calls `main` as a function returning no value, then [exits with code zero](https://github.com/openvm-org/openvm/blob/538c5488130da56c8442d33445efe3c1fe5ea8b8/crates/toolchain/openvm/src/process.rs#L3-L6). On the monitor's unmerged [termination tests](https://github.com/eth-act/zkevm-test-monitor/blob/b41462a50e3e69b24faf933f2f30759141ac6ccf/results/history/openvm-eth-act-standards.json), guests whose `main` returns 1 or 7 finish normally ([issue #52](https://github.com/eth-act/zkevm-test-monitor/issues/52)). Panics exit with code 1, and the [aggregation circuit requires exit code zero](https://github.com/openvm-org/openvm/blob/538c5488130da56c8442d33445efe3c1fe5ea8b8/crates/continuations/src/circuit/inner/vm_pvs/air.rs#L138-L140), so a panicking execution cannot yield a verifying proof.

The other reviewed rows remain unknown:

- **Final proof size ≤300 KiB — ❓:** The [2.1 Preview announcement](https://blog.openvm.dev/2.1) reports STARK proofs under 300 kB at 100 bits of provable security, and [soundcalc estimates](https://github.com/ethereum/soundcalc/blob/2af5e7dfc01e4aef1bc0e544a3b75c1940b1dded/reports/openvm2.md#L13-L14) a worst-case final proof of 270 KiB for v2.0.0 at 100 bits. The reviewed SDK [ships only 100-bit parameter presets](https://github.com/openvm-org/openvm/blob/538c5488130da56c8442d33445efe3c1fe5ea8b8/crates/sdk/src/config.rs#L5-L6), so no size exists for the handbook's 128-bit configuration.
- **Instruction address misaligned exception semantics — ❓:** The interpreter [finds instructions by `pc / 4`](https://github.com/openvm-org/openvm/blob/538c5488130da56c8442d33445efe3c1fe5ea8b8/crates/vm/src/arch/interpreter.rs#L611-L614), so a jump to an address that is 2 mod 4 appears to run the instruction at the rounded-down address, which the standard forbids, while the rvr executor [rejects unaligned PCs](https://github.com/openvm-org/openvm/blob/538c5488130da56c8442d33445efe3c1fe5ea8b8/crates/rvr/rvr-openvm/c/openvm_state.h#L50-L56). A test should jump to such a target on both execution paths and check for abnormal termination and a rejected proof.

<summary>SP1</summary>

This review covers [`b8387fa6` (`v6.9.0`)](https://github.com/succinctlabs/sp1/tree/b8387fa61e1361d90ee7de49f551863418ca0f08); `main` at `02fa3018` adds only documentation and CI changes. Test results come from the [monitor](https://github.com/eth-act/zkevm-test-monitor/blob/0d09b4363a5a4392aba2a7d28102700314f75fd5/config.json#L6-L19), which now pins upstream `f5a5bbf6` (`v6.6.0`, the version ere uses) instead of a fork; the files behind the I/O, termination, linker-script, memory-operation, and randomness findings are unchanged between v6.6.0 and v6.9.0.

- **Host randomness — 🔴:** [`sys_rand`](https://github.com/succinctlabs/sp1/blob/b8387fa61e1361d90ee7de49f551863418ca0f08/crates/zkvm/entrypoint/src/syscalls/sys.rs#L5-L52) draws from a guest-side PRNG with a fixed seed, so values repeat across executions, and SP1 exports no `zkvm_random_u64`. On v6.6.0, all six of the monitor's unmerged [randomness tests](https://github.com/eth-act/zkevm-test-monitor/pull/49) fail.
- **Documented cluster-mode support tested on the EF cluster — 🟡:** [SP1 Cluster](https://github.com/succinctlabs/sp1-cluster/blob/e8a552bdd2cb158ce3f241cc1e0d5d686ee38db5/README.md) documents a multi-GPU proving service with a coordinator, workers, and a Kubernetes deployment, but its [BSL 1.1 license](https://github.com/succinctlabs/sp1-cluster/blob/e8a552bdd2cb158ce3f241cc1e0d5d686ee38db5/LICENSE) permits production use only on the Succinct Prover Network. [Provoor](https://github.com/han0110/provoor/blob/7fc2b947123104b0d91dc4fa37b3f91e2a4995bb/README.md#zkvms) lists only ZisK and OpenVM, and the review found no SP1 run on the EF cluster.
- **RISC-V target — 🔴:** The [latest standard ISA run](https://eth-act.github.io/zkevm-test-monitor/zkvm.html?name=sp1&suite=act4-standard&run=latest) tests upstream v6.6.0 through ere on September 29, 2026 (ACT4 4.1.0) and passes 62 of 72 tests: `I-auipc-00` and eight `Misalign-*` load/store tests fail at execution, and `I-fence-00` executes but the prover rejects FENCE ([monitor issue #51](https://github.com/eth-act/zkevm-test-monitor/issues/51)). The [executor rejects misaligned loads and stores](https://github.com/succinctlabs/sp1/blob/b8387fa61e1361d90ee7de49f551863418ca0f08/crates/core/executor/src/vm.rs#L517-L590) in v6.9.0 as well, so SP1 lacks the required `Zicclsm` support. [PR #2979](https://github.com/succinctlabs/sp1/pull/2979), released in v6.8.1, fixes AUIPC sign extension in the x86 JIT and may resolve `I-auipc-00`, but no monitor run covers it.
- **I/O interface — 🟡:** All 15 I/O tests in the [October 1 standards run](https://eth-act.github.io/zkevm-test-monitor/zkvm.html?name=sp1&suite=eth-act-standards&run=latest) pass execution, proving, and verification on v6.6.0. [`read_input`](https://github.com/succinctlabs/sp1/blob/b8387fa61e1361d90ee7de49f551863418ca0f08/zkevm/libzkevm/src/io.rs#L46-L76), however, drains the first input chunk on its first call, whereas the standard requires it to do so during initialization. The [documented host contract](https://github.com/succinctlabs/sp1/blob/b8387fa61e1361d90ee7de49f551863418ca0f08/zkevm/README.md#L133-L137) also requires the whole input in one chunk.
- **Cryptographic accelerators C interface — 🟡:** In the October 1 run on v6.6.0, 11 of the 19 functions pass, but all seven `zkvm_bls12_*` functions fail on point encoding, and `zkvm_ripemd160` writes its digest to the wrong end of the buffer. [PR #2865](https://github.com/succinctlabs/sp1/pull/2865), released in v6.9.0, adopts the EIP-2537 encoding and right-aligns the digest, but no monitor run covers it, and [standards issue #35](https://github.com/eth-act/zkevm-standards/issues/35) on BLS12-381 encoding remains open. The functions also [return `ZKVM_EFAIL` on NULL pointers](https://github.com/succinctlabs/sp1/blob/b8387fa61e1361d90ee7de49f551863418ca0f08/zkevm/libzkevm/src/precompile/hash.rs#L24-L33) instead of panicking as the header recommends.
- **Accelerated memory operations — 🟡:** `libzkevm.a` exports a strong `memcpy` [defined next to `_start`](https://github.com/succinctlabs/sp1/blob/b8387fa61e1361d90ee7de49f551863418ca0f08/crates/zkvm/entrypoint/src/lib.rs#L249-L250), and the October 1 run passes all nine memory tests it ran on v6.6.0. The library has no strong `memmove`, `memset`, or `memcmp`, so the monitor [skipped their link tests](https://github.com/eth-act/zkevm-test-monitor/blob/976088ef71f03d62afd32d512b9d3f71c9e57dac/tests/eth-act-standards/build-guests.sh#L90-L105). The standard requires vendors to document their linking mechanism, and SP1 does not. [Standards issue #48](https://github.com/eth-act/zkevm-standards/issues/48) asks whether partial acceleration conforms.
- **Static library and linker script — 🟡:** `libzkevm.a` provides `_start`, the I/O functions, all 19 accelerators, and `abort`, and [`zkvm.ld`](https://github.com/succinctlabs/sp1/blob/b8387fa61e1361d90ee7de49f551863418ca0f08/zkevm/zkvm.ld#L32-L117) defines `_heap_start` and `_heap_end`. The script, however, has no `PHDRS` declaration, so GNU ld emits a writable and executable segment that SP1's own loader rejects; the monitor [patches the script](https://github.com/eth-act/zkevm-test-monitor/issues/58) to link its tests. The `main` return-value gap below also applies.
- **ELF loading and validation — 🟡:** The [loader](https://github.com/succinctlabs/sp1/blob/b8387fa61e1361d90ee7de49f551863418ca0f08/crates/core/executor/src/disassembler/elf.rs#L96-L111) accepts ELF32 as well as ELF64 and checks only that `e_entry` is aligned, not that it lies in an executable segment. [PR #2981](https://github.com/succinctlabs/sp1/pull/2981), released in v6.8.1, stopped zero-fill from overwriting file bytes but left these checks unchanged.
- **Execution termination semantics — 🟡:** [`__start` forwards `(exit_code & 0xff) as u8`](https://github.com/succinctlabs/sp1/blob/b8387fa61e1361d90ee7de49f551863418ca0f08/crates/zkvm/entrypoint/src/lib.rs#L245-L246), so a `main` return of 256 becomes exit code 0 and counts as success. In execution-only runs of the monitor's unmerged [termination tests](https://github.com/eth-act/zkevm-test-monitor/blob/b41462a50e3e69b24faf933f2f30759141ac6ccf/results/history/sp1-eth-act-standards.json), SP1 reports error codes 1 and 7 when `main` returns 1 and 7.

The other reviewed rows remain unknown:

- **Final proof size ≤300 KiB — ❓:** ere [proves](https://github.com/eth-act/ere/blob/c0c411ae9215e0f72a00d52e32e267b30ef48606/crates/prover/sp1/src/sdk.rs#L89-L104) and verifies SP1 compressed proofs, which SP1 documents as constant-size STARKs without giving a size. The Groth16 wrapper relies on pairings, which the handbook's security assumptions exclude. Measuring a serialized compressed proof would settle the row.
- **Memory safety guard regions — ❓:** The [load/store address constraint](https://github.com/succinctlabs/sp1/blob/b8387fa61e1361d90ee7de49f551863418ca0f08/crates/core/machine/src/operations/address.rs#L84-L87) rejects addresses below 2^16, which covers the null page and the 64 KiB below the downward-growing stack. The review found no matching check in the executor, so it remains unclear whether such an access ends execution abnormally or only blocks the proof.
- **Instruction address misaligned exception semantics — ❓:** [`Program::fetch`](https://github.com/succinctlabs/sp1/blob/b8387fa61e1361d90ee7de49f551863418ca0f08/crates/core/executor/src/program.rs#L155-L158) indexes instructions by `(pc - pc_base) / 4`, so the executor appears to run the instruction at the rounded-down address when a jump sets bit 1 of the PC. It remains unclear whether the circuit rejects such a PC.

<summary>lambda-vm</summary>

This review covers [`ffc4ac19` (`v0.1.0`)](https://github.com/yetanotherco/lambda_vm/tree/ffc4ac19e755d93ed631ace71f17577478d8d21b); `main` has stayed there since September 22, and every PR merged since then targets `spec/main` or feature branches. The RISC-V status reflects the latest published [standard ISA run](https://eth-act.github.io/zkevm-test-monitor/zkvm.html?name=lambdavm&suite=act4-standard&run=latest), of September 28, 2026, in which all 72 tests pass execution, proving, and verification with ACT4 4.1.0; that run tested `09ef37d9`, a May 29 commit. lambda-vm's own [ACT4 nightly](https://github.com/yetanotherco/lambda_vm/actions/runs/38357239290) passes the same 72 tests at the reviewed commit against an older ACT4 snapshot. lambda-vm has no eth-act standards run ([monitor issue #56](https://github.com/eth-act/zkevm-test-monitor/issues/56)).

- **Host randomness — 🔴:** The [guest RNG](https://github.com/yetanotherco/lambda_vm/blob/ffc4ac19e755d93ed631ace71f17577478d8d21b/syscalls/src/random.rs#L10-L52) seeds `sys_rand` and the `getrandom` backend from a fixed constant inside the guest, so every execution draws the same sequence, and the host supplies no values. The source exports no `zkvm_random_u64`.
- **Documented cluster-mode support tested on the EF cluster — 🔴:** The vendor's [public roadmap](https://yetanotherco.github.io/lambda_vm_roadmap/) lists distributed proving as not started. ere [supports lambda-vm on CPU only, without GPU or cluster proving](https://github.com/eth-act/ere/blob/c0c411ae9215e0f72a00d52e32e267b30ef48606/README.md#L166-L170), and [Provoor](https://github.com/han0110/provoor/blob/7fc2b947123104b0d91dc4fa37b3f91e2a4995bb/README.md#L39-L44) deploys only ZisK and OpenVM.
- **Final proof size ≤300 KiB — 🔴:** The [README](https://github.com/yetanotherco/lambda_vm/blob/ffc4ac19e755d93ed631ace71f17577478d8d21b/README.md#L7) states that proof compression is still under development, so the release emits only base STARK proofs. [PR #980](https://github.com/yetanotherco/lambda_vm/pull/980) measured a 729,298,288-byte proof for mainnet block 25368371, and ere's lambda-vm [test proof](https://github.com/eth-act/ere/blob/c0c411ae9215e0f72a00d52e32e267b30ef48606/crates/verifier/lambdavm/tests/fixtures/proof.bin) is 14.9 MB.
- **I/O interface — 🟡:** The [SDK exports `read_input` and `write_output` with C linkage](https://github.com/yetanotherco/lambda_vm/blob/ffc4ac19e755d93ed631ace71f17577478d8d21b/syscalls/src/ef_io.rs#L33-L68); input reads are idempotent, and output concatenates. The [executor, however, caps total public output at 1 MiB](https://github.com/yetanotherco/lambda_vm/blob/ffc4ac19e755d93ed631ace71f17577478d8d21b/executor/src/vm/memory.rs#L203-L219) and returns an error beyond that limit; the standard requires every `write_output` call to succeed and specifies no such cap.
- **Cryptographic accelerators C interface — 🔴:** The reviewed source exports none of the 19 `zkvm_*` functions. The guest SDK reaches its Keccak and secp256k1 accelerators only through [Rust functions](https://github.com/yetanotherco/lambda_vm/blob/ffc4ac19e755d93ed631ace71f17577478d8d21b/syscalls/src/syscalls.rs#L160-L198).
- **Accelerated memory operations — 🔴:** The source exports none of `memcpy`, `memmove`, `memset`, and `memcmp`, so guests fall back to the toolchain's routines. The standard makes acceleration optional, so this conforms; the 🔴 marks the missing acceleration. Open [PR #874](https://github.com/yetanotherco/lambda_vm/pull/874) adds a DMA-backed `memcpy`, and open [PR #984](https://github.com/yetanotherco/lambda_vm/pull/984) extends it to `memmove` and `memset`.
- **Static library and linker script — 🔴:** lambda-vm ships a [Rust guest crate](https://github.com/yetanotherco/lambda_vm/blob/ffc4ac19e755d93ed631ace71f17577478d8d21b/syscalls/Cargo.toml) and a [target spec](https://github.com/yetanotherco/lambda_vm/blob/ffc4ac19e755d93ed631ace71f17577478d8d21b/executor/programs/riscv64im-lambda-vm-elf.json) that links with LLD's default layout, but no static library and no linker script, so it defines no `_heap_start` or `_heap_end`.
- **Memory layout restrictions — 🔴:** Source constants, not a vendor linker script, fix the memory map: the [heap runs from `_end` to `0xC0000000`](https://github.com/yetanotherco/lambda_vm/blob/ffc4ac19e755d93ed631ace71f17577478d8d21b/syscalls/src/allocator.rs#L816-L822), [private input starts at `0xFF000000`](https://github.com/yetanotherco/lambda_vm/blob/ffc4ac19e755d93ed631ace71f17577478d8d21b/executor/src/vm/memory.rs#L49-L52), and the [executor sets the stack top](https://github.com/yetanotherco/lambda_vm/blob/ffc4ac19e755d93ed631ace71f17577478d8d21b/executor/src/vm/registers.rs#L3-L16). The test monitor wrote its own [linker script](https://github.com/eth-act/zkevm-test-monitor/blob/0d09b4363a5a4392aba2a7d28102700314f75fd5/zkvms/lambdavm/isa-configs/lambdavm-rv64im-zicclsm/link.ld) from these constants.
- **Memory safety guard regions — 🔴:** The [executor's memory](https://github.com/yetanotherco/lambda_vm/blob/ffc4ac19e755d93ed631ace71f17577478d8d21b/executor/src/vm/memory.rs#L60-L127) is a sparse map over the whole 64-bit address space: unwritten addresses read as zero, writes succeed at any address, and [no memory error](https://github.com/yetanotherco/lambda_vm/blob/ffc4ac19e755d93ed631ace71f17577478d8d21b/executor/src/vm/memory.rs#L284-L295) covers an unmapped or guarded region. A null-pointer access therefore does not end execution, and the stack has no guard below it.
- **ELF loading and validation — 🟡:** The [loader](https://github.com/yetanotherco/lambda_vm/blob/ffc4ac19e755d93ed631ace71f17577478d8d21b/executor/src/elf.rs#L271-L370) checks ELF64, little-endian RISC-V executables and loads `PT_LOAD` segments, but classifies executable segments by the `PF_X` bit alone. It accepts writable executable segments, overlapping segments, and an `e_entry` outside any executable segment.
- **Execution termination semantics — 🟡:** The [entry point](https://github.com/yetanotherco/lambda_vm/blob/ffc4ac19e755d93ed631ace71f17577478d8d21b/syscalls/src/entrypoint.rs#L6-L16) calls `main` without capturing a return value, then invokes [`sys_halt`, which supplies exit code zero](https://github.com/yetanotherco/lambda_vm/blob/ffc4ac19e755d93ed631ace71f17577478d8d21b/syscalls/src/syscalls.rs#L141-L153), so a non-zero C `main` return ends as success. The vendor's [allocator notes](https://github.com/yetanotherco/lambda_vm/blob/ffc4ac19e755d93ed631ace71f17577478d8d21b/syscalls/src/allocator.rs#L57-L77) also state that Rust `abort()` and some panic paths can fall through to `pc == 0`, which the executor treats as normal completion.

The other reviewed rows remain unknown:

- **EF Cryptography review — ❓:** lambda-vm has no configuration in [soundcalc](https://github.com/ethereum/soundcalc/tree/2af5e7dfc01e4aef1bc0e544a3b75c1940b1dded/soundcalc/zkvms), where the Cryptography team's review starts, and open draft [PR #1016](https://github.com/yetanotherco/lambda_vm/pull/1016) fixes unconstrained columns that, according to the PR, let the verifier accept false statements.
- **Instruction address misaligned exception semantics — ❓:** The [executor rejects any PC that is not 4-aligned](https://github.com/yetanotherco/lambda_vm/blob/ffc4ac19e755d93ed631ace71f17577478d8d21b/executor/src/vm/execution.rs#L115-L117) before fetching, and the prover's [DECODE table](https://github.com/yetanotherco/lambda_vm/blob/ffc4ac19e755d93ed631ace71f17577478d8d21b/prover/src/tables/decode.rs#L309-L318) holds only word-aligned PCs, so a misaligned fetch appears unprovable. No fault test has run through proof verification.
